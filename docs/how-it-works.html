Before you dig

Reading Rust in two minutes

Before the code, a phrasebook. If you've written PowerShell scripts you already know most of these ideas; Rust just spells them differently. fn is function. let makes a variable, and it can't change unless you say mut. A struct is a record with named fields, like a PSCustomObject. match is switch. The two ideas that are really Rust are Option and Result. Option means 'there might be nothing here' and Rust makes you check before you use it, which wipes out null-reference crashes. Result means 'this might have failed', and the question mark means: if it failed, stop here and pass the error up, like a throw. Arc and Mutex are how threads share data safely: a shared object with a lock on it.

LEVEL 1 · THE SURFACE

What you actually see

Before we open anything up, here is what the app does from the outside. The two LED panels, one each side of the keyboard, become little screens: a system monitor, a clock, an audio visualizer, games, maths animations, your own drawings. The RGB keyboard and macropad get lighting effects and key mapping. And there's a tray icon by the clock that you can right-click. That's the whole user-facing story. Everything else on this page is about how that happens.

The life of one frame

Here's the whole journey of one picture, start to finish, with the file that does each step. Ten times a second, the main loop wakes up. It reads numbers from Windows, like how much memory is in use. Each app draws itself into a 9 by 34 grid. The grid goes into a queue that only ever keeps the newest frame, so a slow panel never falls behind and shows old data. LEVEL 2 · THE IRON

Meet the hardware

Each LED panel is not just a bunch of lights: it is a tiny computer of its own, built around a Raspberry Pi RP2040 chip, the same chip as a Raspberry Pi Pico. When you plug it in, Windows sees it as a USB serial port, a COM port, exactly like a USB-to-serial console cable you'd use on a switch. Its USB ID is 32AC:0020: 32AC is Framework's vendor number. The keyboard and macropad are different: they show up as HID devices, the same class as any keyboard or mouse, and they run QMK, a popular open-source keyboard firmware. The laptop itself is the third piece: Windows supplies all the numbers that end up on the panels.

Sysadmin translation A panel is a serial console; the keyboard is a HID device.

Go deeper: show me the codereal code, with notes

How the code recognises each device

Everything the app knows about the hardware starts with a few constants. The LED panel's USB vendor and product IDs are 32AC and 0020, exactly what you'd see in Device Manager under the device's hardware IDs. The keyboard and macropad share Framework's vendor ID with their own product IDs, and White Rabbit talks to them on usage page FF60, the private VIA channel, in 32-byte reports. Then a one-line rule decides whether a COM port is a panel: either its IDs match, or Windows describes it as an LED Matrix Input Module. In Rust, u16 just means a 16-bit number, and the 0x prefix means hexadecimal.

  1. The panel's ID cardFramework's USB vendor ID and the LED Matrix product ID: the same values Device Manager shows.
  2. The keyboard'sSame vendor, its own product IDs. FF60 is the private VIA channel next to the typing one.
  3. Is this COM port a panel?Yes if the IDs match, or if Windows' description says so. Some(...) means 'there is a value'.

The map of the rabbit hole

WhiteRabbitWindow.exe is the settings window, and it only exists while you have it open. Six crates, two programs

The code is split into six crates. A crate is Rust's word for a package or module, a bit like a DLL except it's built into the exe rather than shipped beside it. Two of them become programs: wr-monitor builds WhiteRabbit.exe, and wr-window builds WhiteRabbitWindow.exe. The other four are libraries both programs share. wr-core holds all the drawing and has no Windows code at all, which is why it can be tested on Linux. wr-panel knows how to talk to the panels, wr-music does the audio analysis, and wr-keyboard talks to the keyboard. Because the window uses the same wr-core as the monitor, the preview in the window is drawn by exactly the same code as the real panels.

LEVEL 4 · THE ALWAYS-ON PART

WhiteRabbit.exe: a service in disguise

WhiteRabbit.exe behaves a lot like a Windows service, even though technically it's a normal program with a tray icon. It starts at login from the Run key in the registry, which is the same list you see in Task Manager's Startup tab, and if you disable it there, White Rabbit respects that. It uses a mutex, a system-wide 'I'm already running' flag, so a second copy can't start and fight over the panels. It keeps both COM ports open the whole time, draws every frame, watches the lid and sleep events, and listens for the Ctrl+Alt+Shift shortcuts. All of that in about 6 megabytes.

Startup, line by line

This is the start of WhiteRabbit.exe, trimmed. First it checks the single-instance lock: if a copy is already running, this one just opens the window and quits. Next it looks for the panels. At sign-in, USB devices can still be appearing, so it tries up to 15 times, two seconds apart. Then it starts one drawing thread per panel, so each panel gets its own worker and a slow one can't hold up the other. It opens the control pipe for the window, starts the main loop on its own thread, and finally hands the main thread to the tray icon, which runs until you click Quit. That's a pattern you'll recognise from services: initialise, spin up workers, then wait for a stop signal.

  1. Already running?A named mutex. If found, just open the window and exit.
  2. Wait for USBAt sign-in the panels may not exist yet: 15 tries, 2 s apart.
  3. A worker per panelEach panel gets its own thread, fed by a queue.
  4. Open the pipeStarts answering the window's requests.
  5. Hand over to the trayRuns until Quit, then everything shuts down.

Hearing the lid close

How does the app know you've shut the lid? The tray icon has a hidden window, and every Windows window gets messages. At startup the app registers for two power notifications: the lid switch and the console display state. Windows then sends WM_POWERBROADCAST messages, and this match statement sorts them: lid changed, screen turned on or off, PC suspending, PC resuming. Each one becomes a power event, which sets a shared flag. The main loop checks that flag ten times a second and, if it's set, plays the old-TV switch-off and sends the panels to sleep. If you've ever set up a scheduled task triggered by a power event in Event Viewer, this is the program-side version of that.

  1. The lid switchA power setting the app asked Windows to report (RegisterPowerSettingNotification).
  2. Screen on or offSame message, a different GUID.
  3. Sleep and wakeClassic suspend and resume messages. Each sets a flag the main loop reads.

LEVEL 5 · THE CONTROL PANEL

The window is just the console

The window you click around in is a completely separate program, WhiteRabbitWindow.exe. Think of services.msc: closing the console doesn't stop the service. Same here. Close the window and its memory is handed back; the panels carry on. When you flip a switch in the window, it doesn't touch the panels itself. It sends a short message over a named pipe to the always-on part, like 'set brightness to 60' written in JSON, which is just a structured text format. The pipe is locked down: only your Windows user can open it, and only from this PC, not over the network.

Sysadmin translation Services.msc vs the service: closing it stops nothing.

LEVEL 6 · SHARING NICELY

Only one program may hold a COM port

Here's a real-world snag. Windows lets only one program open a serial port at a time, just as only one person can be on a switch's console port. The always-on part holds both panel ports. So how does the window show a live preview or let you play Snake? It borrows. It sends 'hold' and the monitor stops drawing on that panel, like putting a server into maintenance mode. Then the window sends its drawing commands through the monitor, which passes them along. When it's done it sends 'release'. And if the window crashes mid-game, a watchdog notices its process ID has gone and takes the panel back, so you're never stuck with a frozen Snake.

Sysadmin translation One console session per port, plus maintenance mode.

Go deeper: show me the codereal code, with notes

Borrowing a panel, and the watchdog

Two pieces of code make the sharing work. When the window sends hold, the monitor records which ports are held and the process ID of the window that asked. From then on, the panel's drawing thread still runs, but the hub drops its frames for that port, so only the window's commands reach the panel. The second piece is a tiny thread named holders. Every two seconds it asks Windows whether each holder's process is still alive. If the window has crashed or been killed in Task Manager, its panels are released and the monitor is told to redraw. Two seconds later, your system monitor is back. It's the same idea as a lease with a heartbeat.

  1. Who's asking?The window sends its own process ID with the request.
  2. Lend the portsThe hub now drops the monitor's frames for these ports.
  3. A 2-second heartbeatA tiny thread called 'holders' wakes every 2 s.
  4. Holder gone? Take it backIf that process no longer exists, release and redraw.

LEVEL 7 · THE WIRE

Speaking panel: bytes down a serial line

How does a picture get onto a panel? Down the serial line at 115,200 baud, in tiny messages. Every message starts with the same two bytes, 32 AC, a sort of 'hey, panel'. Then a command number, then any data. To draw, White Rabbit sends 'stage column' for each column that has something lit, carrying the 34 brightness values for that column, then one 'flush' to show them all at once, so you never see a half-drawn frame. Columns that are completely dark are skipped to save time. If you've ever typed AT commands to a modem, it's the same idea, just in bytes rather than letters.

Sysadmin translation AT commands to a modem: stage the changes, then commit.

Go deeper: show me the codereal code, with notes

Turning a picture into bytes

This short function is the whole translation from picture to wire. It takes the grid and walks across its 9 columns. A column that's completely dark is skipped, because the panel starts every frame dark anyway. For every other column it builds a stage-column command: the column number followed by its 34 brightness values. After the last column it adds one flush command, and the panel shows the new frame all at once. Each command gets the two magic bytes 32 AC on the front. One more detail lives in panel.rs: each command is written to the port separately, because the firmware reads one command per USB transfer, and if a frame is identical to what's already shown it isn't sent again.

  1. Dark column? Skip itThe panel starts each frame dark, so there's nothing to send.
  2. Stage a columnColumn number, then its 34 brightness values (0x07).
  3. FlushShow every staged column at once (0x08): no half-drawn frames.
  4. The magic prefixEvery message starts 32 AC, then the command.

LEVEL 8 · ROLL CALL

Which panel is the left one?

Two identical panels, two COM port numbers, and Windows hands those numbers out in whatever order it likes. So how does White Rabbit know which one is on the left? It asks Windows where each device is plugged in: the USB location path, which is like knowing a server's rack and slot rather than its hostname. The left and right slots of the Framework 16 always have the same location. If that information isn't available it falls back to the USB ID and makes a sensible guess, and if the guess is wrong you can swap the panels in Settings or use 'Teach my ports' to pin each side.

Sysadmin translation Find a server by rack and slot, not by its DHCP address.

Go deeper: show me the codereal code, with notes

Deciding left from right

This is the function that sorts the panels. First it filters the list of every serial port on the PC down to just the LED panels, keeping each one's USB location and COM name. Then it sorts them by USB location, and since the laptop's left slot always comes first in that order, the first panel found is the left one. That's the normal case. If you've used Teach my ports or swapped the panels, those choices are saved as pins in the layout file, and the rest of the function honours them before falling back to the sorted order. The |p| syntax is a tiny inline function, the same idea as $_ in a PowerShell Where-Object.

  1. Only the panelsEvery COM port on the PC, filtered to the ones that are panels.
  2. Sort by USB locationThe left slot sorts first, so it becomes the left panel.
  3. Your overridesTeach my ports and Swap panels are saved as pins.
  4. No pins? DoneFirst found is left, second is right.

LEVEL 9 · THE DASHBOARD

System monitor: perfmon on 306 LEDs

The system monitor is the headline feature. Every second or so, the always-on part collects numbers, mostly from the same places Task Manager and Performance Monitor read them: CPU and memory from Windows itself, GPU use from the same 'GPU Engine' performance counters Task Manager uses, disk and network rates, the battery. Temperatures and fans come from Framework's own control service or Libre Hardware Monitor. Weather comes from the internet, and 'now playing' from the same media controls the Windows volume pop-up shows. A layout file decides what goes where: each panel is split into a top and bottom half, and each half has a playlist of apps that take turns.

Sysadmin translation Perfmon counters on a tiny wall dashboard.

Go deeper: show me the code2 parts

The main loop

This is the heartbeat of the app. run is a loop that keeps going until Quit sets the quit flag. Each pass calls step, which returns how long to wait, normally 100 milliseconds, so the loop runs about ten times a second. Inside step, the rotation works out which app each half-panel should show right now, from the playlists in the layout file. Then, for each panel, it makes a blank grid, asks render_panel_on to draw that panel's apps into it using the latest readings, and puts the finished grid in that panel's queue. Notice that it never touches a COM port itself: the drawing threads do that, so a missing or slow panel can never freeze the loop.

  1. Loop until QuitEach pass returns how long to rest: 100 ms.
  2. Whose turn is it?The layout's playlists decide which app shows in each half.
  3. DrawA blank 9×34 grid, filled in by that panel's apps.
  4. Hand it overInto the queue. The drawing thread does the slow USB part.

From a Windows number to lit LEDs

Let's follow one number all the way. The memory reading calls GlobalMemoryStatusEx, the same Windows API that Task Manager's memory figure comes from. It works out the fraction of physical memory in use, a number between 0 and 1. That number goes to draw_memory in wr-core, which turns it into lit pixels: the memory bar is 7 pixels wide and 2 rows tall, so 14 steps, and it fills the top row and bottom row to match. fill_x lights a run of pixels in one row with the current brightness. This split is deliberate: the Windows-specific reading lives in wr-monitor, and the drawing, which is the same on every platform, lives in wr-core where it can be tested.

  1. Ask WindowsThe same API Task Manager's memory figure comes from.
  2. A fractionUsed ÷ total: 0.0 to 1.0.
  3. 14 stepsThe bar is 7 pixels wide and 2 rows tall.
  4. Light the pixelsfill_x lights a run of pixels in one row.

LEVEL 10 · THE DISCO

Audio reactivity: a graphic equaliser

Audio reactivity listens to whatever the laptop is playing. It uses a Windows feature called WASAPI loopback, which lets a program hear the sound going to the speakers without touching it: think of it as a port mirror, or a SPAN port, but for audio. Then a bit of maths called an FFT splits the sound into bass, middle and treble, exactly what the sliders on an old hi-fi graphic equaliser represent. Each column of LEDs becomes a frequency band and lights up with how loud that band is. Both panels share one recording, so they always move in step, and when the music stops you get a calm idle version of the look instead of a dead screen.

Sysadmin translation A SPAN port for sound, read through a graphic equaliser.

Go deeper: show me the codereal code, with notes

Splitting sound into bars

This is the maths behind the bars, and it's less scary than it looks. The sound comes in as 48,000 numbers a second; the analyser looks at the latest 4,096 of them, about 85 milliseconds. First it smooths the edges of that slice with a window function, so the cut-off doesn't sound like a click. Then the FFT, a fast Fourier transform, turns 'how the speaker moves over time' into 'how much of each pitch there is'. The bins are the pitch ranges for each bar, spaced in octaves from deep bass to treble, like the sliders on a graphic equaliser. Each band's energy is converted to decibels, and a later step maps the decibels onto a bar 0 to 34 pixels tall.

  1. Smooth the edgesA window function, so the cut-off slice doesn't add a click.
  2. The FFTTurns 'wobble over time' into 'how much of each pitch'.
  3. One band per barOctave-spaced pitch ranges, bass to treble.
  4. To decibelsLoudness in dB; later scaled to a bar 0-34 tall.

LEVEL 11 · THE CANVAS

Everything is a 9 × 34 picture

Here's a nice simplification: whatever is on the panel, a game of Snake, a Lorenz attractor, your drawing, the clock, it's all the same thing underneath. A grid of 9 by 34 numbers, each from 0 to 255. Each app's only job is to fill in that grid; the panel layer then sends it down the wire. Effects like slide, fade and pixel rain are just ways of mixing yesterday's grid into today's. And because every picture is just numbers, the project can test it automatically: the expected pictures are saved as 'golden frames', and every build checks that each app still draws them pixel for pixel.

The grid, and the test that guards it

Here's the grid itself: a struct with one field, v, which is 9 columns of 34 numbers. That's the whole data type every app draws into. Below it is the golden-frame test. LEVEL 12 · THE KEYS

The keyboard and macropad

The keyboard side came from a separate app that has now moved inside White Rabbit. Keyboards don't have COM ports; they're HID devices. Alongside the normal typing channel, QMK firmware can open a second, private channel called raw HID. White Rabbit sends 32-byte messages on that channel: 'set this effect', 'paint this key', 'here is the sound level'. Your typing never goes through it. Like the panels, the always-on part drives the lighting while the window is closed, and the window borrows it while you're editing. Key mapping changes are written into the keyboard itself, so they work on any computer, even without White Rabbit.

Sysadmin translation An out-of-band port, like iDRAC or iLO.

Go deeper: show me the codereal code, with notes

Painting the keyboard, 8 keys at a time

When the app draws a lighting effect itself, for the audio show for example, it has a colour for every LED and needs to get them to the keyboard. encode_frame chops that list into chunks of 8 LEDs. Each chunk becomes one 32-byte HID message: where the chunk starts, how many LEDs are in it, then red, green and blue for each. set wraps it with the VIA header: 07 for set, a channel byte, and the value ID for a frame. Why only 8 LEDs when 9 would fit? The comment in the code explains: the keyboard's chip sometimes receives only 31 of the 32 bytes, so the app never relies on the last one. That's the kind of hard-won hardware lesson that ends up in comments.

  1. 8, not 9The chip sometimes drops the 32nd byte, so it's never used.
  2. Chop into chunks8 LEDs per message.
  3. Red, green, blue3 bytes per LED, after the start and count.
  4. Wrap itVIA header: 07 = set, then the 'frame' value ID.

LEVEL 13 · THE CHIP

Inside the panel: the firmware

Firmware is the program that lives inside the panel, on its own chip, and it's written in Rust too. It does a few simple jobs in a loop: read a command from USB, update its picture, and push the picture out to the LED driver chip, an IS31FL3741, that actually powers the 306 LEDs. White Rabbit's version of the firmware adds a startup animation setting. That setting is stored in a small 4 KB area of the chip's flash memory, which survives power-off, a bit like the CMOS settings in a BIOS. The panel also looks after itself: if nothing has talked to it for a minute, or the laptop suspends the USB port, it fades out and sleeps.

Sysadmin translation The startup animation is a BIOS setting kept in CMOS.

Go deeper: show me the codereal code, with notes

Inside the panel: the firmware's loop

This code runs on the panel's own chip, in the inputmodule-rs repo. The firmware is one big loop. Each time round, it checks whether the PC sent anything over USB. If a command arrived and parses correctly, three things happen: any startup animation still playing is cancelled, the sleep timer is reset, and the command is handled. Then comes a line with a story. Originally the LEDs were redrawn after every command, so a frame of ten commands redrew the LEDs ten times and the panels lagged behind the app. White Rabbit's firmware skips the redraw for stage-column commands and only redraws on flush. And if nothing arrives for 60 seconds, the timer check sends the panel to sleep.

  1. Anything from the PC?Read the USB serial line and decode the command.
  2. Reset the sleep timerAny message keeps the panel awake (and stops the startup animation).
  3. Redraw only on flushWhite Rabbit's fix for laggy panels: no redraw per staged column.
  4. 60 s of silenceNothing heard for a minute? Fade out and sleep.

LEVEL 14 · THE UPGRADE

Updating firmware without a screwdriver

Updating the panel's firmware is surprisingly low-tech, and that's a good thing. The app sends one command, 'go to the bootloader'. The panel reboots into a built-in recovery mode that's burned into the RP2040 chip and can't be broken, and in that mode it shows up on your PC as a USB drive called RPI-RP2. Copying the ledmatrix.uf2 file onto that drive installs it, and the panel restarts with the new firmware. It's exactly like flashing a BIOS from a USB stick, except the panel is the USB stick. Because the recovery mode lives in read-only memory, a bad update can always be fixed by doing it again.

Sysadmin translation A BIOS flash from a USB stick (the panel is the stick).

Go deeper: show me the codereal code, with notes

Flashing firmware, in code

This is the window's flash function, and it reads almost like the four steps above. It reads the .uf2 file into memory. It looks for an RPI-RP2 drive, which it recognises by an INFO_UF2.TXT file on it. If there isn't one yet, it sends the panel the one-byte bootloader command, closes the port because the panel is about to vanish, and waits for the drive to appear. Then it simply writes the firmware to a file on that drive. The chip's bootloader does the rest. Finally it waits for the drive to disappear, which means the panel has restarted, so that flashing the second panel doesn't accidentally write to the first one again. The question marks pass any error straight up to show you.

  1. Find the driveAny drive letter with INFO_UF2.TXT on it is a panel in bootloader mode.
  2. Reboot the panelOne command (0x02). The panel vanishes and comes back as a drive.
  3. Copy the fileLiterally a file copy. The chip does the rest.
  4. Wait for the restartSo the next panel doesn't get flashed twice.

LEVEL 15 · THE REWRITE

Why rewrite it all in Rust?

White Rabbit started life in Python, which is lovely to write but has two problems for an app like this. First, to ship Python as a Windows exe, a tool called PyInstaller packs the whole Python runtime into a self-extracting bundle. Antivirus programs see a lot of malware packed the same way, so they flagged the app. Second, all that runtime sits in memory: about 66 MB for the background part. Rust compiles straight to a normal Windows program: no interpreter, no unpacking: about 8 MB in the first Rust version and about 6 MB today. The Python version wasn't thrown away: it became the reference, and the Rust code is tested against pictures Python drew, pixel for pixel.

Go deeper: show me the codereal code, with notes

How Rust keeps it small and safe

Part of the small size comes from these five lines in Cargo.toml, the release build settings. opt-level s tells the compiler to optimise for size rather than raw speed. lto, link-time optimisation, lets it look across all six crates and every library at once and throw away anything that's never called. codegen-units 1 trades a slower build for a tighter result. panic abort means that if something goes badly wrong, the program logs it and stops, rather than carrying extra machinery to recover. strip removes the debugging symbols from the exe. The safety side isn't a setting at all: it's the compiler refusing to build code that might use missing data or share memory between threads without a lock.

  1. Size over speedOptimise for a small exe.
  2. Link-time optimisationLooks at all the code at once and drops what's never called.
  3. Fail fastA crash is logged, then the program stops cleanly.
  4. No debug symbolsStrips the exe down to what runs.

LEVEL 16 · WHERE THE BODIES ARE BURIED

The sysadmin's cheat sheet

If you ever need to troubleshoot White Rabbit, this is where everything lives. Settings and the layout file are in your roaming AppData folder; the log is in local AppData and is kept under a megabyte. The startup entry is a normal Run key value called WhiteRabbit. The pipe's lock and key

Here's where two lines on the cheat sheet come from. address builds the pipe's name from the app name and your Windows user name, so two people signed in to the same PC get separate pipes. When the monitor starts, new_key makes 32 random bytes and writes them to control.key in your local AppData. Every connection starts with a handshake that proves the other side knows that key, before any request is read. On top of that, the pipe itself is created so that only your user can open it and remote clients are refused. So another user, or another machine on the network, can't tell your panels what to do. A new key is made every time the monitor starts.

  2. A fresh secret32 random bytes in control.key, new at every start.
  3. Prove you know itA handshake before anything else is read.
  4. Size limitRequests over 16 MB are refused.

LEVEL 17 · CHANGE MANAGEMENT

From idea to installer

Finally, how a change gets from an idea to your laptop. Every change goes on its own branch and gets a pull request, which is a proposal: 'here's what I want to change'. GitHub Actions, a build server in the cloud, then spins up a fresh Windows machine, runs the tests including the pixel-for-pixel golden frames, opens the app and clicks through every page as a smoke test, and builds the installer. A link to that test build appears on the pull request. Only after it's been tried on real hardware does it get merged, and a release is a separate, deliberate button press. It's change management, with the robot doing the boring checks.

The robot that clicks every page

Good news for a sysadmin: the build pipeline's checks are written in PowerShell. This is part of the smoke test that runs on a fresh Windows machine in GitHub Actions for every change. It starts the window with --list-apps and --diagnose, waits up to two minutes for each to finish, and fails the build if either hangs or exits with an error. Then it opens the real window with a special smoke-test setting that visits every page, and checks the log file to make sure each page reported that it was shown. If any page is missing, the build goes red and nobody gets a broken installer. You could run the same commands by hand on your own machine.

  1. Run itThe real exe, on a fresh Windows machine in the cloud.
  2. Hang = failTwo minutes to finish, or it's killed and the build fails.
  3. Read the logEvery page must write 'shown' to the log.
  4. Collect failuresAny missing page turns the build red.
